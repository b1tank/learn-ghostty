## What are we trying to do?

Chapter 01 put application ownership in `App`. But `src/main.zig` still had two jobs:

1. be the executable's root file;
2. start the Ghostty application.

Chapter 02 separates those jobs. The root file becomes a tiny router. The application startup moves to `main_ghostty.zig`.

You can think of the router as a typed switchboard:

```text
zig build
  → build.zig chooses src/main.zig
  → src/main.zig reads build_config.zig
  → .ghostty selects main_ghostty.zig
  → main_ghostty.main creates App
```

There is no runtime menu. The compiler resolves this route while building the executable.

## File 1: `build.zig`

Purpose: tell Zig what to compile, install, run, and test.

<CodeSnapshot file="src/data/reconstruction/chapter-02/build.zig" label="build.zig" status="adapted" reason="Minimal build graph for one executable and one test artifact." />

### Import and build function

```zig
const std = @import("std");
```

`@import("std")` gives us the Zig standard-library namespace. This is not textual inclusion like a C header. No file is loaded at runtime.

```zig
pub fn build(b: *std.Build) void {
```

- `pub fn` declares a visible function.
- `b: *std.Build` is a pointer to Zig's build context.
- `void` means the function returns no value.

Zig's build runner calls this function. The function creates a graph of work. It does not compile each target immediately as the line executes.

**C mental model:** a typed function that configures Make or CMake targets.

### Target and optimization options

```zig
const target = b.standardTargetOptions(.{});
const optimize = b.standardOptimizeOption(.{});
```

Both locals use inferred types.

- `const` means the local binding cannot be reassigned.
- `.{}` is an empty options struct whose type comes from the function parameter.
- `target` stores the requested operating system and CPU target.
- `optimize` stores Debug or a release optimization mode.

Zig does not require a written type for an initialized local variable.

### Root module

```zig
const root_module = b.createModule(.{
    .root_source_file = b.path("src/main.zig"),
    .target = target,
    .optimize = optimize,
});
```

This creates one module description.

- `.root_source_file` says where compilation begins.
- `b.path(...)` makes a path relative to the project.
- `.target` and `.optimize` copy the choices above.
- The leading dots are field names in an inferred struct literal.

The important line for this chapter is:

```zig
.root_source_file = b.path("src/main.zig")
```

That is why the compiler enters through the router.

### Executable and install step

```zig
const exe = b.addExecutable(.{
    .name = "ghostty-from-scratch",
    .root_module = root_module,
});
b.installArtifact(exe);
```

`addExecutable` adds an executable node to the graph. `installArtifact` connects it to the normal install step.

Expected installed path:

```text
zig-out/bin/ghostty-from-scratch
```

**C mental model:** define an executable target, then add it to an install target.

### Run step

```zig
const run = b.addRunArtifact(exe);
run.step.dependOn(b.getInstallStep());
```

The first line creates a step that can run the executable. The second line says installation must finish first.

```zig
if (b.args) |args| run.addArgs(args);
```

`b.args` is optional. It either contains no value or contains an argument slice.

```zig
if (optional_value) |payload|
```

means: enter the body only when a value exists, and call that value `payload`.

**C mental model:** `if (args != NULL)`, except Zig narrows the optional value to its non-null payload.

```zig
const run_step = b.step("run", "Run ghostty-from-scratch");
run_step.dependOn(&run.step);
```

This exposes:

```console
zig build run
```

`&run.step` takes the step's address. The dependency points from the public `run` command to the actual executable-run step.

### Test step

```zig
const tests = b.addTest(.{ .root_module = root_module });
const run_tests = b.addRunArtifact(tests);
const test_step = b.step("test", "Run the Zig tests");
test_step.dependOn(&run_tests.step);
```

These four lines:

1. create a test artifact from the same root module;
2. create a step that runs that artifact;
3. expose a public step named `test`;
4. connect the public step to the test runner.

That gives us:

```console
zig build test
```

The final `}` closes the `build` function.

## File 2: `src/build_config.zig`

Purpose: represent the build's entrypoint choice as a Zig type.

<CodeSnapshot file="src/data/reconstruction/chapter-02/build_config.zig" label="src/build_config.zig" status="adapted" reason="Static one-entry replacement for Ghostty's generated build configuration." />

```zig
pub const ExeEntrypoint = enum {
    ghostty,
};
```

This declares a public enum type named `ExeEntrypoint`.

- `enum` creates a closed set of tags.
- `ghostty` is the only tag in this checkpoint.
- `};` closes and terminates the type declaration.

**C mental model:**

```c
typedef enum {
    EXE_ENTRYPOINT_GHOSTTY,
} ExeEntrypoint;
```

The Zig tag belongs to its type. It is not an unchecked global integer macro.

```zig
/// The build-selected executable entrypoint.
```

`///` is a documentation comment for the declaration directly below it.

```zig
pub const exe_entrypoint: ExeEntrypoint = .ghostty;
```

Read it from left to right:

- `pub`: importing modules may access it;
- `const`: the declaration cannot be rebound;
- `exe_entrypoint`: its name;
- `: ExeEntrypoint`: its explicit type;
- `= .ghostty`: its value.

The expected type lets Zig shorten:

```zig
ExeEntrypoint.ghostty
```

to:

```zig
.ghostty
```

## File 3: `src/main.zig`

Purpose: select the application entry module at compile time.

<CodeSnapshot file="src/data/reconstruction/chapter-02/main.zig" label="src/main.zig" status="adapted" reason="The executable root reduced to the only reconstructed entrypoint." />

### Import the configuration namespace

```zig
const build_config = @import("build_config.zig");
```

`@import` returns the imported file's namespace. The local name `build_config` gives us access to:

```zig
build_config.ExeEntrypoint
build_config.exe_entrypoint
```

This is a compile-time module dependency, not runtime loading.

### Select a module

> **Text version:** The typed build value selects the `main_ghostty.zig` namespace at compile time. The root module then aliases that namespace's `main` function directly.

```zig
const entrypoint = switch (build_config.exe_entrypoint) {
```

A Zig `switch` can produce a value. Here that value will be a module namespace.

The input is a compile-time-known constant, so this does not add a runtime branch.

```zig
    .ghostty => @import("main_ghostty.zig"),
```

- `.ghostty` is the enum case to match.
- `=>` separates the case from its result.
- `@import(...)` produces the selected namespace.
- The trailing comma ends the switch arm.

```zig
};
```

The brace closes the switch. The semicolon terminates the `entrypoint` declaration.

### Publish the selected function

```zig
pub const main = entrypoint.main;
```

This does not create a wrapper like:

```zig
pub fn main() !void {
    return entrypoint.main();
}
```

It gives the selected function another public name. There is no extra runtime call frame.

`pub` controls Zig namespace visibility. It does not by itself export a C ABI symbol.

### Force the route into tests

```zig
test {
    _ = entrypoint;
}
```

Zig has built-in test declarations. This one has no display name.

Zig analyzes declarations lazily. Referencing `entrypoint` makes the selected module reachable during `zig build test`.

`_` is the discard target. It says we intentionally use the value only to make it reachable.

**C mental model:** `(void)entrypoint;` explains the discard, but not Zig's lazy semantic analysis.

## File 4: `src/main_ghostty.zig`

Purpose: start the Ghostty application after the router selects it.

<CodeSnapshot file="src/data/reconstruction/chapter-02/main_ghostty.zig" label="src/main_ghostty.zig" status="adapted" reason="Chapter 01 startup moved intact behind the selected entry module." />

### Imports

```zig
const std = @import("std");
const App = @import("App.zig");
```

The first line imports the standard library. The second imports the `App.zig` file container.

Because `App.zig` has fields, its file container is also the `App` struct type. `App` therefore acts as both:

```text
a type
+
a namespace containing App functions
```

### Fallible main

```zig
/// The application entrypoint selected by src/main.zig.
pub fn main() !void {
```

The comment documents the function.

`!void` means:

```text
success → no value
failure → an inferred error
```

The possible allocation failure from `App.create` becomes part of `main`'s return type.

**C mental model:** `int main(void)` is close in shape, but C's integer status is only a convention.

### Traces

```zig
std.debug.print("[entry] ghostty\n", .{});
std.debug.print("[main] process started\n", .{});
```

`std.debug.print` writes formatted bytes to standard error.

- `\n` is one line-feed byte.
- `.{}` is an empty tuple of formatting arguments.

There are no replacement fields in these strings, so the tuple is empty.

### Ownership scope

```zig
{
```

This inner block controls when `defer` runs.

```zig
const app = try App.create(std.heap.page_allocator);
```

Read this from right to left:

1. use the page allocator;
2. ask `App.create` for an App;
3. if creation fails, `try` returns that error from `main`;
4. otherwise bind the returned `*App` to `app`.

The local type is inferred.

`const app` fixes the pointer binding. It does not make the pointed-to App immutable.

**C mental model:**

```c
App *const app = app_create(page_allocator);
if (app == NULL) return 1;
```

```zig
defer app.destroy();
```

This schedules destruction for the end of the current inner block.

It is structured cleanup. It is not a promise that cleanup survives forced process termination.

```zig
app.run();
```

Dot-call syntax resolves this as:

```zig
App.run(app);
```

There is no hidden class or virtual table.

```zig
}
```

Leaving the block runs the deferred `app.destroy()`.

```zig
std.debug.print("[main] process exiting\n", .{});
}
```

The final trace therefore happens after App destruction. The last brace ends `main`. Reaching it means successful `void` completion.

## File 5: `src/App.zig`

Purpose: allocate one stable App, initialize it, and free it in the right order.

<CodeSnapshot file="src/data/reconstruction/chapter-02/App.zig" label="src/App.zig" status="adapted" reason="Chapter 01 App ownership remains unchanged while startup moves behind the router." />

### Name the current container

```zig
const App = @This();
```

`@This()` returns the current file container type. Since this file declares fields, that container is the `App` struct.

**C mental model:** `typedef struct App App;` is close, but `@This()` returns the actual enclosing Zig type.

```zig
const std = @import("std");
const Allocator = std.mem.Allocator;
```

The first line imports the standard library. The second creates a short local alias for the allocator interface type.

### App field and error set

```zig
/// General-purpose allocator used to own the stable App pointer.
alloc: Allocator,
```

The comment documents the field. Zig fields use `name: Type` order. The App stores its allocator because it will need the same allocator when it destroys itself.

```zig
pub const CreateError = Allocator.Error;
```

`CreateError` is a public alias for the allocator's error set. Allocation is the only fallible operation at this checkpoint.

### Create

```zig
pub fn create(alloc: Allocator) CreateError!*App {
```

The return type parses as:

```text
CreateError ! *App
```

It contains either an allocation error or a non-null pointer to one App.

```zig
const app = try alloc.create(App);
```

`alloc.create(App)` reserves correctly sized and aligned storage for one App. `try` propagates allocation failure and unwraps the successful pointer.

**C mental model:** typed `malloc(sizeof(App))` plus an immediate failure check.

```zig
errdefer alloc.destroy(app);
```

`errdefer` runs only if a later error exits this function. It prevents leaks during fallible initialization.

In Chapter 02 the remaining operations cannot fail, so this cleanup edge is currently dormant.

```zig
app.init(alloc);
std.debug.print("[app] created\n", .{});
return app;
}
```

- `app.init(alloc)` resolves to `App.init(app, alloc)`.
- The print emits the creation trace.
- `return app` transfers the pointer to the caller.
- The brace closes `create`.

The caller now owns the obligation to call `destroy`.

### Initialize

```zig
pub fn init(self: *App, alloc: Allocator) void {
```

`self` is an ordinary explicit pointer parameter. Zig has no implicit C++ `this`.

```zig
self.* = .{ .alloc = alloc };
```

- `self.*` dereferences the pointer.
- `.{ .alloc = alloc }` is an App struct literal inferred from the assignment target.

**C mental model:**

```c
*self = (App){ .alloc = alloc };
```

The closing brace ends `init`.

### Deinitialize fields

```zig
pub fn deinit(self: *App) void {
    _ = self;
}
```

`deinit` will eventually release resources stored inside App. There are none yet.

`_ = self` deliberately discards the unused parameter.

**C mental model:** `(void)self;`

### Destroy the allocation

```zig
pub fn destroy(self: *App) void {
    const alloc = self.alloc;
```

The function first copies out the allocator. After the App is freed, reading `self.alloc` would be use-after-free.

```zig
self.deinit();
std.debug.print("[app] destroyed\n", .{});
alloc.destroy(self);
}
```

The order is deliberate:

```text
save allocator
→ release App-owned fields
→ print trace
→ release App storage
```

After `alloc.destroy(self)`, `self` is invalid.

### Temporary run method

```zig
pub fn run(self: *App) void {
    _ = self;
    std.debug.print("[app] running\n", .{});
}
```

This function does not use App state yet, so it discards `self` and prints one line.

It is temporary. Chapter 03 moves event-loop ownership out of shared App state.

### Built-in test

```zig
test "create and destroy App" {
    const app = try App.create(std.testing.allocator);
    app.destroy();
}
```

Zig's test runner discovers this named test.

`std.testing.allocator` tracks allocations. If `app.destroy()` were missing, the test allocator would report a leak.

## Put the whole runtime together

Here is a C-shaped mental model. It is not a direct translation because it loses Zig's checked error union and compile-time namespace selection.

```c
typedef struct App {
    Allocator alloc;
} App;

App *app_create(Allocator alloc) {
    App *app = allocator_create(alloc, sizeof(App));
    if (app == NULL) return NULL;

    *app = (App){ .alloc = alloc };
    fprintf(stderr, "[app] created\n");
    return app;
}

int ghostty_main(void) {
    fprintf(stderr, "[entry] ghostty\n");
    fprintf(stderr, "[main] process started\n");

    App *app = app_create(page_allocator);
    if (app == NULL) return 1;

    app_run(app);
    app_destroy(app);

    fprintf(stderr, "[main] process exiting\n");
    return 0;
}
```

The Zig version improves three boundaries:

1. failure is represented in the function type;
2. `defer` keeps cleanup attached to the owning scope;
3. the entry module is selected by typed compile-time code.

## What is still wrong?

`main_ghostty` still calls:

```zig
app.run();
```

That makes shared App state pretend it owns every platform's event loop. GTK, macOS, browsers, and embedding hosts do not run the same way.

Chapter 03 introduces a headless platform runtime and one Surface-shaped session boundary. It still does not add a PTY, parser, or window.
