## The limitation

Chapter 01 put application ownership in `App`, but `src/main.zig` still mixed two roles:

```text
operating-system entrypoint
+
Ghostty application startup
```

Ghostty's build produces more than its graphical application: helper generators and documentation tools also need executable roots. Duplicating the whole build graph for every root would make configuration drift likely.

The next boundary is a tiny router.

<FrontierMap current="App lifecycle" />

The implementation frontier remains headless. Routing is build structure, not a runtime, Surface, or terminal session.

## How the router appeared historically

In February 2024, commit `f1227a3` moved roughly 315 lines from `main.zig` into `main_ghostty.zig`. The former application entrypoint became a ten-line build-selected router. A January 2025 build refactor replaced `usingnamespace` with explicit exports close to today's form.

## The route

<RoutingDiagram />

`switch` sees a compile-time-known enum value. Only the selected import becomes the executable's `main` implementation.

## Step 1: represent the build choice

<CodeSnapshot file="src/data/reconstruction/chapter-02/build_config.zig" label="src/build_config.zig" status="adapted" reason="A static one-entry substitute for Ghostty's generated typed build options." />

```zig
pub const ExeEntrypoint = enum { ghostty };
pub const exe_entrypoint: ExeEntrypoint = .ghostty;
```

This file is deliberately not generated yet. Generation would add machinery without changing the one available choice. The important boundary is that source code consumes a typed build decision rather than command-line text.

## Step 2: make main only a router

<CodeSnapshot file="src/data/reconstruction/chapter-02/main.zig" label="src/main.zig" status="adapted" reason="The current router reduced to the only reconstructed entrypoint." />

The key line is an exported declaration, not a wrapper function:

```zig
pub const main = entrypoint.main;
```

Zig exposes the selected module's function as the root executable entrypoint. There is no extra runtime call frame whose only job is forwarding.

The test block forces semantic analysis of the selected module during `zig build test`.

## Step 3: move application startup

<CodeSnapshot file="src/data/reconstruction/chapter-02/main_ghostty.zig" label="src/main_ghostty.zig" status="adapted" reason="The Chapter 01 lifecycle moved intact; global initialization, CLI actions, and a platform runtime remain omitted." />

The new trace:

```zig
std.debug.print("[entry] ghostty\n", .{});
```

is temporary instrumentation. It proves the selected module runs before `App.create` without pretending another subsystem exists.

## The next limitation

`main_ghostty` still calls `App.run()`. Current Ghostty does not: a selected platform runtime owns the native event loop and calls into shared App state.

Chapter 03 introduces a headless runtime and one Surface-shaped session boundary:

```text
main_ghostty → shared App
             → platform runtime App → run
                                  ↘ Surface
```

No native toolkit or PTY is needed to prove that ownership split.
